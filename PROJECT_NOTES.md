Добавлено 2026-09-24 после жалобы «переключаюсь по разделам — язык сбрасывается на казахский»: каждая страница — полная загрузка (не SPA), поэтому `currentLang` обнулялась. Теперь `applyLanguage()` пишет выбор в `localStorage`, при инициализации читается оттуда (`translations[storedLang] ? storedLang : "kz"`), в try/catch.

Пользователь предлагал HTMX для этой задачи — сознательно не стал: HTMX решило бы проблему только для кликов по меню, но не для прямого перехода по ссылке/F5. Если понадобится плавная навигация без перезагрузки — `hx-boost` на `<body>` в `base.html`.

**Переводы неполные**: у `kz` и `en` в `script.js` нет ключей `partner.*` — откат `translate()` на `ru`, так и задумано.

**Якоря в общей шапке:** «О компании»/«Контакты» — якоря на разделы главной (`/#about`), остальное — страницы. Плавный скролл в `script.js` path-aware: `a[href*="#"]` + сравнение `new URL(link.href).pathname` с `location.pathname` — скроллит только на текущей странице, иначе обычная навигация. «Проекты» в меню с 2026-09-28 ведут на `/projects/…`, не на якоря.

## Django-монолит (2026-09-24, по прямой просьбе: «подключи фронтенд в django через шаблонизатор, чтобы сайт был цельным монолитом»)

До этого: статические `index.html`/`styles.css`/`script.js` в корне `psa-landing/` + отдельный Django-бэкенд только под `/api/` и `/admin/`, фронтенд ходил за данными через `fetch()` (см. предыдущую задачу «подключи фронтенд» — это был промежуточный этап, теперь уже неактуальный).

Что сделал:
- `index.html` → `backend/templates/index.html` (Django-шаблон, `{% load static %}`, 4 раздела — `{% for entry in ...entries %}` вместо `<div id="...-list">` + JS fetch).
- `styles.css` → `backend/static/styles.css` (без изменений, просто перенос).
- `script.js` → `backend/static/script.js` — **вырезан весь блок «5. Контент с бэкенда»** (API_URL, loadApiCollection, createFeedItem и т.д., ~120 строк) — он больше не нужен, контент теперь рендерится сервером до отправки HTML браузеру. Всё остальное (i18n, мобильное меню, модалки проектов, валидация формы) — без изменений.
- `content/views.py`: добавлена `home(request)` — собирает все 4 queryset'а, рендерит `index.html` с контекстом. Старые `ReadOnlyModelViewSet` под `/api/` оставлены нетронутыми (уже не используются сайтом, но могут пригодиться внешним потребителям — см. `backend/README.md`).
- `psa_backend/urls.py`: `path('', home)` — корень теперь отдаёт страницу, не 404.
- `psa_backend/settings.py`: `TEMPLATES[0]['DIRS'] = [BASE_DIR/'templates']`, `STATICFILES_DIRS = [BASE_DIR/'static']`.
- **Старые `index.html`/`styles.css`/`script.js` в корне `psa-landing/` удалены** — сознательно, чтобы не было двух расходящихся копий фронтенда. Если увидишь, что они снова появились — это либо откат пользователем (см. «Паттерн» выше), либо кто-то намеренно вернул старую статическую версию; не мой косяк переноса.

Проверено (Playwright): страница рендерится, даты в правильном русском формате («01 января 2026 г.» — через Django template filter `|date:"d E Y"`, не JS `toLocaleDateString` как раньше), i18n-переключатель/мобильное меню/модалки проектов работают как прежде (их код не трогал), статика (`/static/styles.css`, `/static/script.js`) отдаётся, ошибок в консоли нет.

**Важное отличие от прежнего фронтенд-рендеринга:** раньше я вручную собирал DOM через `createElement`/`textContent`, чтобы обезопасить вставку данных с бэкенда (не доверять `innerHTML`). В Django-шаблонах это не нужно — `{{ entry.title }}` автоэкранируется движком по умолчанию, инъекция потребовала бы явного `|safe`, которого нигде не ставил.

## Разделение на отдельные страницы (2026-09-24, тем же днём, сразу после монолита)

Прямая просьба: «сделай так чтобы разделы... открывались в отдельной странице через меню. С главной страницы удали». Третий заход на эту же идею за сессию (см. «История» выше) — но впервые с нормальной шаблонизацией, поэтому сделал качественно иначе, не просто скопировал прошлый HTML-вариант:

- Ввёл `backend/templates/base.html` — шапка/меню/модалка проектов один раз, все 5 страниц через `{% extends %}`. Раньше (в откаченной HTML-версии) шапка была буквально скопирована в каждый файл — сам же отметил это в заметках как источник риска рассинхрона. Теперь это невозможно физически.
- 4 новые вьюхи в `content/views.py` (`local_content_page`, `procurement_page`, `documents_page`, `news_page`) + `home()` упрощена — больше не собирает 4 queryset'а, эти секции убраны со страницы.
- `psa_backend/urls.py`: 4 новых `path()`, `/local-content/`, `/procurement/`, `/documents/`, `/news/`.
- **script.js переписан для мульти-страничности**: раньше `a[href^="#"]` (чистый якорь) матчил только ссылки вида `#about`. Теперь шапка общая на все страницы и ссылки на разделы главной выглядят как `/#about` (абсолютный путь + якорь) — старый селектор бы их не поймал вообще, плавный скролл сломался бы молча. Переписал на `a[href*="#"]` + сравнение `new URL(link.href).pathname` с `location.pathname` — подробности в «Грабли» ниже.

Проверено (Playwright): на главной 4 раздела отсутствуют, все 5 URL отдают 200, плавный скролл на `/` работает для `#about` (реальный скролл, без перезагрузки), переход с `/local-content/` по ссылке `/#contacts` — обычная навигация + нативный якорь долетает до секции, данные из БД показываются на всех 4 страницах.

## Rich-text в админке (2026-09-24) — УСТАРЕЛО, заменено Wagtail (см. ниже)

Просьба была неоднозначная («улучши админку, чтобы могли редактировать текст») — уточнил через AskUserQuestion, выбрали «форматирование текста в уже существующих полях» (не «сделать статичный контент главной редактируемым» — это осталось как было, захардкожено в шаблонах).

- `content/widgets.py` — `QuillWidget(forms.Textarea)`: рендерит обычную (скрытую) textarea + контейнер редактора Quill поверх, JS с CDN (`cdnjs.cloudflare.com/ajax/libs/quill/1.3.7`) синхронизирует HTML из Quill в textarea при каждом изменении (`text-change`). Никакого pip-пакета (не django-ckeditor) — специально, чтобы не зависеть от совместимости стороннего Django-приложения с Django 6.1 (очень свежий релиз, риск несовместимости реальный).
- `content/admin.py`: `formfield_overrides = {models.TextField: {"widget": QuillWidget}}` на `LocalContentEntryAdmin`, `ProcurementEntryAdmin`, `NewsEntryAdmin` (у `DocumentEntry` нет TextField — не применимо). `NewsEntry.excerpt` — это `CharField`, не `TextField`, редактором не накрывается (осталось обычным однострочным полем, так и задумано — это краткая подпись, не текст для форматирования).
- Поле в БД как было `models.TextField` — миграций не потребовалось, просто хранит HTML вместо голого текста.
- **Шаблоны обновлены**: `{{ entry.body }}` → `{{ entry.body|safe }}` (иначе Django заэкранирует HTML-теги и на сайте покажутся буквально `&lt;p&gt;`), обёртка `<p>` → `<div>` (Quill выдаёт свои `<p>`/`<ul>` — вложенный `<p>` внутри `<p>` невалиден). Задето: `local_content.html` (`body`), `procurement.html` (`description`), `news.html` (`body`, но не `excerpt` — та осталась в `<p>` без `|safe`, обычный текст).
- `styles.css`: добавлены стили для вложенных тегов внутри `.feed-item-text` (`p`, `ul`/`ol`/`li`, `a`, `strong`, `h2`/`h3`) — раньше там ожидался только голый текст.

**Модель доверия та же, что была у PocketBase-editor-полей** (см. «Грабли» ниже, уже задокументировано раньше на другом бэкенде) — HTML пишет только аутентифицированный суперюзер через `/admin/`, поэтому `|safe` безопасен. Если когда-то появится текстовое поле, куда сможет писать не-админ (форма на сайте) — для него `|safe` нельзя, нужен обычный экранированный текст.

Проверено (Playwright): зашёл в `/admin/`, создал новость, напечатал текст с жирным фрагментом через панель Quill, сохранил — на публичной `/news/` жирный текст отрендерился как настоящий `<strong>`, не как экранированный текст. Открыл запись на редактирование — форматированный текст корректно подгрузился обратно в редактор (round-trip работает). Тестовую запись удалил после проверки.

## Картинки в редакторе + страница на каждую запись «Местное содержание» (2026-09-24) — УСТАРЕЛО, заменено Wagtail (см. ниже)

Прямая просьба: «в местном содержании каждая запись должна иметь свою страницу. Оформление текста должен ещё включать добавление картинки». Два независимых изменения в одном заходе.

**Картинки в Quill** — решал между (а) base64 прямо в HTML-поле (это то, что Quill делает из коробки без доп. настройки — просто работает, но раздувает `TextField` и вес страницы с каждой картинкой, база в итоге распухнет) и (б) реальной загрузкой файла на сервер. Выбрал (б):
- `content/views.py`: `quill_image_upload` — `@staff_member_required` (та же проверка, что у `/admin/` — специально не публичный эндпоинт, иначе любой мог бы заливать файлы), `@require_POST`, валидирует `content_type` (`image/*`) и размер (≤8МБ), сохраняет через `default_storage` в `media/quill_uploads/`, возвращает `{"url": ...}`.
- `content/widgets.py`: кастомный `image`-handler на панели Quill — открывает file picker, шлёт файл через `fetch()` с `X-CSRFToken` (читает `csrftoken` из cookie, Django admin сам его выставляет через `{% csrf_token %}` на форме), вставляет `<img src="...">` с реальным URL через `quill.insertEmbed`.
- `styles.css`: `.feed-item-text img { max-width: 100%; ... }` — иначе картинка шире контейнера могла бы вызвать горизонтальный скролл страницы.
- `media/quill_uploads/` — не в git (уже был `media/` в `.gitignore` с прошлой сессии, под документы; картинки редактора идут туда же).

**Страница на запись** — только для `LocalContentEntry` (просьба была именно про «местное содержание», Закупки/Документы/Новости не трогал):
- `content/views.py`: `local_content_detail(request, pk)` — `get_object_or_404` + рендер.

## Грабли, на которые уже наступал (актуально, если делать похожие вещи снова)

- **`[hidden]` перебивается CSS того же уровня специфичности**, если у элемента есть класс с `display:flex/block` — правило класса может победить (одинаковая специфичность, но позже в каскаде). Чинится явным `.selector[hidden] { display: none; }`.
- **`.parent ul` (descendant selector) ловит и вложенные `<ul>`** — например, дропдаун «Проекты» внутри `.main-nav` случайно наследовал `display:flex` от общего правила навигации. Использовать `.main-nav > ul` (прямой потомок) — этот фикс, кстати, единственный из «навигационных» уже закреплён в текущем состоянии (`c16f55e`), не откатился.
- **Hero был «кривым»** из-за двойного назначения класса `.container` (даёт `margin-inline:auto`) + свой `max-width` на одном и том же элементе — центрировался отдельно от остальных секций. Разделять: внешний `.container` для паддингов/центрирования, внутренний элемент — только ограничение ширины текста, без своего `margin:auto`.
- **`<title>`/`<meta description>` не подключены к i18n-системе** (`translate()`/`data-i18n` их не трогает) — при смене языка по умолчанию их обновлять вручную отдельно.
- **Плавный скролл по якорям ломается молча при переходе на общую шапку для нескольких страниц.** Селектор `a[href^="#"]` матчит только чистые якоря (`#about`); как только ссылки на разделы главной страницы стали `{% url 'home' %}#about` (т.е. реальный href `/#about`) в общем `base.html`, такие ссылки перестали матчиться вообще — не ошибка в консоли, просто плавный скролл тихо переставал работать на главной. Фикс: матчить `a[href*="#"]`, резолвить `new URL(link.href)` и сравнивать `.pathname` с `location.pathname` — включать плавный скролл только для ссылок на текущую страницу, иначе пропускать (браузер сам перейдёт и долетит до якоря нативно).
- **PocketBase-специфика (если снова возьмём этот бэкенд):** `editor`-поля хранят HTML из доверенного источника (только суперюзер через `/_/`) — их можно рендерить через `innerHTML` осознанно; для полей, куда потенциально сможет писать кто-то ещё (форма на сайте, не через админку) — только `textContent`. PocketBase не работает как SQLite-файл на Vercel serverless (нет постоянной ФС) — нужен отдельный постоянный хост с диском (или сам локальный запуск, как было здесь).
